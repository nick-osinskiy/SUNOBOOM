# Разработка и продакшен

Версия приложения остаётся v0.220. Разделение веток не является новым выпуском приложения или этапом миграции Vue.

- `main` — проверенная версия для продакшена: https://nick-osinskiy.github.io/SUNOBOOM/
- `codex/develop` — постоянная ветка разработки. Все следующие изменения начинаются здесь или в отдельных `codex/*` ветках от неё.
- В `main` изменения попадают через Pull Request после проверки `verify-and-build`. Прямые push, force push и удаление main запрещаются защитой ветки, включая администратора. Обязательное одобрение другого участника не требуется: проект может выпускать один владелец.

## Обычная работа

1. Обновить `codex/develop` и выполнить задачу. Не продолжать старую практику прямых коммитов в main из исторических разделов PROJECT_CONTEXT.md.
2. Запустить необходимые локальные проверки, отправить коммит в ветку разработки. GitHub Actions проверяет imports, доменные/маршрутные тесты, production build и полный browser smoke. Из этой ветки сайт не публикуется.
3. Для выпуска открыть Pull Request `codex/develop` → `main`. Перед слиянием обязательны успешные проверки и актуальность относительно main.
4. Слияние Pull Request — действие выпуска. После него Actions повторно собирает и проверяет main; только успешный результат публикуется на Pages. При ошибке остаётся предыдущая опубликованная версия.
5. Синхронизировать develop с main после выпуска. Для merge commits использовать обычный merge/fast-forward, не force push.

В workflow больше нет автоматических коммитов bundle в main. Production artifact собирается из tracked файлов конкретного коммита с заменой dist/vue на только что проверенную сборку. Содержимое node_modules, .git и локальные незакоммиченные файлы в него не попадает. Tracked dist остаётся для запуска существующих локальных smoke tests; перед проверкой/выпуском выполняется build.

GitHub Pages настроен на GitHub Actions, а не на независимую публикацию каждого push. Разработка не имеет отдельного публичного тестового сайта в рамках этой настройки. Для будущего собственного сервера точку публикации можно заменить, сохранив разделение веток и проверки.

Для отката создаётся Pull Request с отменой проблемного изменения; он проходит те же проверки. Данные пользователей, локальные JSON/IndexedDB и аудио эта настройка не изменяет.

При первичной настройке CI/workflow устанавливается административным коммитом в main до включения защиты; дальнейшая работа идёт по правилам выше. Фактические результаты проверок и настроек фиксируются в PROJECT_CONTEXT.md.
